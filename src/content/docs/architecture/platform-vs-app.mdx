application teams opt a service in. ECS does the wiring in between.

On deploy, ECS evaluates every gateway on the cluster and connects the service to each
**compatible** one.

## Compatibility

A gateway is eligible only when **all three** checks pass:

| Check              | Rule                                                                                                                   |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| Access type        | Gateway scheme maps to PUBLIC or PRIVATE; connector `filters.accessTypes` must allow it (omit filter to accept either) |
| VPC                | Gateway subnets and service subnets are in the same VPC                                                                |
| Availability Zones | Gateway has subnets in **every** AZ the service uses                                                                   |

The AZ rule is the one that trips people up — the gateway must cover **every** AZ a service runs
in. Partial overlap is not enough.

## What ECS provisions

Once a service is compatible, ECS creates and manages the load balancer path for you — reusing
shared pieces and adding per-route pieces.

| Scope     | Resources                                                               |
| --------- | ----------------------------------------------------------------------- |
| Shared    | ALB, listener, ALB security group                                       |
| Per route | ACM cert, hostname, listener rule, target group, service security group |

<Aside type="caution">Every managed resource is tagged `AmazonECSManaged=true` plus the gateway and route ARNs. Don't strip those tags — ECS relies on them for updates and cleanup.</Aside>

See [What a connected service creates](/concepts/what-is-ecs-gateway/#what-a-connected-service-creates)
for the full breakdown.
